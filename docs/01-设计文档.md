# InsightAI ChatBI 设计文档

对应代码版本：2026-11-08。平台元库仅 PostgreSQL（SQLite/MySQL 元库支持已移除）。
本文只写"为什么这样设计 + 设计落在哪个文件"，功能表现细节见《功能文档》，操作见《使用文档》，环境搭建见《部署文档》。

---

## 1. 目标与非目标

目标：让高校业务人员（教务、图情档、社科、研招、论文方向等研究背景）用自然语言问数，平台负责把问题翻译成**只读、受行级权限约束、口径可核对**的 SQL，并把结果以表格/图表/指标卡返回，支持多轮追问。

非目标（明确不做，不要再往这里加）：
- 不做数据写入、不做报表编排、不做定时推送。
- 不做通用聊天助手：与数据无关的问题直接拒答。
- 不做自助建模：语义层由管理员维护（同步接入 + 页面手工增强），业务用户只提问。
- 不做指标引擎：指标口径是提示词级约束，不做预计算/物化（见 §3 决策 4）。
- 不追求"SQL 一定正确"，追求"错也不会越权、不会悄悄换口径"。

## 2. 总体架构

```
浏览器 (Vue3 SPA, nginx :8080)
   │  /api/* 同源反向代理，X-Forwarded-For 透传
   ▼
FastAPI (uvicorn :8000)  app/main.py
   ├─ app/api/     auth / chat / meta / code_dict / metric / rbac 六组路由
   ├─ app/auth/    自研 HS256 JWT + 登录口令 + 吊销/限流
   ├─ app/rbac/    角色/部门/用户的服务端校验与不变量
   ├─ app/engine/  LangGraph 问数流水线（核心）+ meta_sync 元数据同步服务
   ├─ app/llm/     私有化 OpenAI 兼容客户端
   ├─ app/rag/     bge-m3 向量 + BM25 混合召回（LanceDB）
   └─ app/models/  SQLAlchemy ORM（平台元库 10 张表）
   │
   ├─▶ 平台元库 PostgreSQL 16（compose 服务 platform-pg）：语义层、全局码表、指标口径、RBAC、会话、审计
   ├─▶ 业务库 StarRocks（只读账号）：被分析的数据，平台不建表
   ├─▶ LanceDB 嵌入式向量索引：backend/data/lance/vecs.lance
   ├─▶ Redis（可选）：令牌吊销表 + 登录限流；空则退化为进程内存
   └─▶ 私有化 LLM（vLLM，OpenAI 兼容）：唯一出网依赖，不出企业内网
```

平台元库 10 张表：`meta_table`、`meta_column`、`code_dict`、`metric`、`department`、`role`、`app_user`、`chat_session`、`chat_turn`、`audit_log`。

进程模型：单容器单 uvicorn 进程。会话状态全部落库，进程内存只放 LLM/embedding 的懒加载单例、LanceDB BM25 缓存和 meta_sync 的任务状态，所以重启不丢业务数据，只丢"重启前随机生成的 TOKEN_SECRET 签出的登录态"和"进行中的同步任务状态"。

## 3. 问数流水线设计

节点编排（`backend/app/engine/pipeline.py`）：

```
analyze ──(intent≠data_query / 寒暄正则命中)──▶ END
  │ next
  ▼
retrieve  向量+BM25 混合召回表(5)与列(30)
  ▼
generate  提示词 = 表结构 + 命中表的指标口径（如有）
  ├─(MISSING_FIELD / REFUSE)──────────▶ END
  ▼
guard     sqlglot AST 护栏：只读校验 + RLS 注入 + LIMIT
  ├─(GuardError)────────────────────▶ END  blocked_by_guard
  ├─(解析异常)──────────────────────▶ correct
  ▼ next
execute   StarRocks 只读查询，fetchmany(limit+1) 判截断
  ├─(DB/超时异常)───────────────────▶ correct
  ▼ chart
chart     图表推荐 + 结果层脱敏/码值翻译 + 回答文案 ─▶ END

correct（自愈）：把报错与原表列清单回喂模型 → 重新 guard，最多 self_correct_retries=2 轮
```

四条关键设计决策：

1. **意图识别与多轮改写合并成一次 LLM 调用**。`analyze` 一次返回 `{"intent","question"}`，避免两次串行调用把这一段的耗时翻倍（`LLM_ENABLE_THINKING=false` 下单次 LLM 调用实测 0.7~1.5s；整条链路还要另加 embedding 召回与业务库执行时间）。历史喂给它的不是纯文本，而是**上轮实际执行的 SQL + 结果列名**，因为业务用户的追问是"再按专业拆一次"这种口径延续，字段名比自然语言描述更可靠。

2. **权限只在代码层强制，提示词只是建议**。提示词里写"平台会自动追加部门过滤"是为了让模型别自己瞎写部门条件；真正的行级权限是 `sql_guard._apply_dept_filter` 对 AST 里**每一个** Select（含子查询）注入 `alias.dept_col = 'v'` 或 `IN (…)`。提示词约束全部当作"能减少错误率"的优化，不作为安全边界。

3. **自愈环不允许改变统计口径**。自愈最容易出的事故是"报错后模型删掉问题要求的维度凑一条能跑的 SQL"，返回一个 status=ok 但口径错了的结果。设计上用机械不变量兜住：`_group_exprs()` 比较自愈前后 SQL 的 GROUP BY 表达式，原来有分组、自愈后没有 → 直接以 `missing_field` 终止，不执行。这条是靠真实事故加上的：「按性别统计学生人数」曾因表里没有性别列，被自愈悄悄改成 `COUNT(*)` 并返回 ok。

4. **指标口径走提示词注入，不做执行层保证（轻量档）**。`retrieve` 命中表后，`metrics_for_tables()` 取出这些表名下的全部指标，`prompt_builder._metrics_block` 把名称/别名/表达式/默认条件/粒度/口径说明渲染进提示词，并追加规则 10 要求模型遵循。被否掉的重方案是指标引擎（把指标编译进 SQL/改写执行计划），代价是要动 guard 与 executor。轻量档的取舍：**无指标时提示词与旧版逐字一致、零影响**；有指标时模型仍可能不遵循，guard 不校验表达式是否被采用——所以指标口径的定位是"统一问法口径的强提示"，不是"硬约束"（见 §8.9）。

## 4. 语义层、码表、指标与向量召回

### 4.1 语义层即白名单

`meta_table`（表 + 部门列）与 `meta_column`（列类型、中文注释、本地码表 enum_dict、敏感标记、全局码表引用）构成"允许提问的白名单"。SQL 生成提示词只渲染这张清单里的表和列（`prompt_builder._ddl_block`）。

### 4.2 码值两层：全局码表 + 列级覆盖

- `code_dict` 存跨表通用码值（如 `sfsc` 有效标识：0=有效/1=无效），列通过 `meta_column.code_dict_id` **引用绑定**，不是复制。理由：几百张表里的同名列（当前环境 sfsc 绑定了 460 列）一处维护、处处生效；复制式下发改一处要追 N 列，必然腐化。
- 列级 `enum_dict` 保留，用于"同名不同义"的局部覆盖。**生效码值 = 全局 entries + 本地 enum_dict（本地覆盖同 key）**，合并逻辑只有 `models/meta.effective_enum()` 一处，提示词渲染（`prompt_builder`）与结果翻译（`presenter`）共用它，保证"生成侧用的码"和"展示侧翻的码"永远一致。
- 删除全局码表时接口先把所有引用列解绑再删（`api/code_dict.delete_dict`），不留悬空 FK。
- 码表内容**不进向量**：召回靠注释，码表只进提示词与结果层，所以改码表即时生效、不需要重建索引。

### 4.3 指标口径

`metric` 表：name（唯一）、aliases、sql_expr、source_table、default_filters、grain、comment。所属表必须是已同步的元数据表（接口校验）。注入范围按召回命中表过滤——问题没命中那张表，指标不进提示词，避免无关口径干扰。grain 只是提示词里的口径说明，不参与任何计算。

### 4.4 注释手工维护与同步的分工

- 列注释同时服务三处：召回、SQL 生成、结果层码值翻译。业务库 `information_schema` 里的注释往往缺失或是英文，所以表/列注释都允许在语义管理页手工改。
- **保存即重嵌入**：`PUT /api/meta/tables|columns` 检测到注释变化后调 `meta_sync.refresh_vectors()`——表向量必刷（表文本含全部列注释摘要），被改的列向量同时刷。这两个 PUT 是同步 `def`，FastAPI 走线程池，嵌入阻塞不卡事件循环。设计理由：改注释是低频管理动作，立即生效比"定时重建"更符合直觉，也省掉运维跑脚本这一步。
- **同步只增不覆盖**（`meta_sync._sync_rows`）：已存在的列整行跳过（注释/码表/敏感标记都不动）；表注释只补空（`mt.comment or 源注释`）；业务库里消失的表/列不删除。理由：同步是"接入新表"的动作，绝不能冲掉管理员手工维护的成果；代价是残留要手工清（见 §8.10）。
- 同步时自动做两件事：按列名/注释正则标敏感列（`phone|mobile|id_card|idcard|identity|身份证|手机号|salary|薪`）；表名以 `dwd|ads|dws` 开头自动归 `trade` 域。同步完成后批量重算这些表及全部列的向量。

### 4.5 同步服务与召回

- `meta_sync` 既是 CLI 脚本的后端，也是页面同步的服务：`POST /api/meta/sync` 起后台线程跑全量同步，`GET /api/meta/sync/status` 轮询进度；进程内互斥，已有任务在跑返回 409。前缀过滤（表名小写 startswith，任一匹配即保留）在拉取之后、截断之前应用；过滤后 0 张表时直接返回，不空调 embedding。
- 召回是 LanceDB 单表 `vecs` + `ns` 字段（tables/columns）分区，向量与 BM25 用 RRF（`1/(60+rank+1)`）融合，**没有任何绝对分数阈值**——设计选择是"宁多不漏，交给选列提示词收敛"。
- 宽表治理：列数 ≤40 时全带注释的列进提示词；>40 时只保留召回命中列 + 有生效码表的列 + `*_id` 列 + 部门列，不足 10 列时按注释补齐，硬上限 50 列。这是为了防止 200+ 列的宽表把提示词撑爆。

## 5. 会话与记忆设计

三层落点（`models/meta.py` + `engine/sessions.py` + `engine/memory.py`）：

| 层 | 存哪 | 内容 | 生命周期 |
|---|---|---|---|
| 会话实体 | `chat_session`（id 即会话 ID，主键） | 标题、归属账号、远期摘要、软删标记 | 长期，删除只置 `deleted` |
| 轮次明细 | `chat_turn` | 原话、改写后问题、实际执行的 SQL、payload（列/行/图/答案） | **仅 status=ok 才写**；删会话时硬删 |
| 远期摘要 | `chat_session.summary` | ≤800 字的**口径**要点，禁含任何统计数值 | 超过 8 个 ok 轮后增量压缩，游标 `summary_from_id` |

设计取舍：
- 上下文窗口只取最近 5 个 ok 轮，更早的轮次不进提示词，而是被压缩成"口径摘要"。摘要只保留对象/表列/时间范围/过滤条件/已确认决定，**显式禁止写入统计数值**（`memory.SUMMARY_SYSTEM`）——数值进摘要会让模型把旧结果当新答案引用。
- 摘要在 `BackgroundTasks` 里生成，不阻塞本次响应。代价是侧栏"已归档口径"标记和摘要内容会晚一拍出现，这是有意接受的（不为它加前端轮询）。
- 会话 ID 由前端 `crypto.randomUUID()` 或 `POST /api/sessions` 生成；`sessions.touch()` 负责用第一条问题认领会话（含把标题取问题前 60 字）。
- 隔离设计：列表/改名/删除按 `user_id` 过滤；`POST /api/chat` 先查 `sessions.owner()`，别人已占用的 ID 直接 403；`GET /api/history/{sid}` 用 `session_id AND user_id` 双条件查，拿不到就返回空列表。

## 6. 权限与数据安全设计

- **令牌只装身份，不装权限**。JWT claims 仅 `sub/username/iat/exp/jti`；角色、部门、单位码每次请求从库重读（`auth/service.load_profile`）。因此改角色、改部门数据权限、停用账号都即时生效，不需要等令牌过期。
- 口令失效链路：自助改口令写 `pwd_changed_at`，`iat < pwd_changed_at` 的令牌一律 401（见 §8.2 已知偏差）。
- 行级权限（RLS）不用数据库原生 RLS，而是 sqlglot AST 改写注入：业务库是 StarRocks，原生策略不支持按用户裁剪；且注入在应用侧可审计——`audit_log` 同时存"模型原始 SQL"和"护栏改写后 SQL"，两条对比就能看出权限是否生效。
- 脱敏在结果层，不在 SQL 层：`presenter.trace_columns` 递归解析血缘（子查询/CTE/UNION/`SELECT *`），把敏感列的标记传播到派生列，再做部分掩码（保留前 ⌈n/4⌉ 与后 ⌊n/4⌋，长度不变，n≤4 全掩）。设计成"部分掩码"而非全掩，是为了让业务用户还能肉眼核对"这个身份证号是不是他要的那条"。
  - 已知且接受的设计边界：聚合/函数包裹的派生值（`COUNT(sfzjh)`、`LEFT(sfzjh,6)`）**不脱敏**——它们已不是原值，强行掩码会毁掉统计结果。
- 管理员旁路：`role.admin` 一个字段同时授予两件事——进四个管理页（语义/码值/指标/权限）、查询结果不脱敏。普通用户即使问法绕弯，也只是被 RLS 限制在自己部门的单位码集合内。
- 只读三重防线：提示词禁止（软）、`FORBIDDEN` AST 节点黑名单 + 根节点类型白名单 + 系统库前缀拦截（硬）、业务库账号本身只有 SELECT 权限（最外层兜底）。

## 7. 技术选型与理由

| 选型 | 理由 | 被否掉的方案 |
|---|---|---|
| FastAPI + LangGraph | 流水线是"带条件回边的 DAG"，自愈重试用 StateGraph 的 route 表达最直白；异步让 LLM 长耗时不占线程 | 手写 if/else 链（回边和状态传递会写成一坨）|
| Vue3 单文件 SPA，无 router/pinia | 一个聊天页 + 四个管理页，`view` ref 切换足够；少一层依赖少一次版本风险 | React（否）、加 vue-router/pinia（过度设计）|
| sqlglot AST 改写 | 需要"对每个 Select 注入过滤"这种语义级改写，字符串拼接在子查询/别名/UNION 上必错 | 正则拼 SQL、DB 原生 RLS（StarRocks 不支持按用户）|
| LanceDB 嵌入式向量 | 私有化环境不引入 Milvus/ES 这类外部服务；单机文件目录即索引，随 `backend/data` 一起备份 | pgvector（否）、Milvus（否）|
| 自研 HS256 JWT（stdlib） | 只需要签/验 + exp + jti 吊销，避免 PyJWT 依赖；`alg` 必须严格等于 HS256 防算法混淆 | python-jose（重）、不签名 cookie（要额外会话存储）|
| bge-m3 本地权重 | 中文列注释召回效果好且可完全离线；torch 走 CPU 轮子避免镜像拉 CUDA | 云端 embedding API（否，数据不出内网是硬要求）|
| psycopg 3 驱动 + naive UTC TIMESTAMP | `DATABASE_URL` 固定 `postgresql+psycopg://`；时间列全用 TIMESTAMP 不用 TIMESTAMPTZ，因为写入侧统一 `datetime.utcnow()`，混用会让锁定窗口和旧令牌判定错位 | asyncpg（同步 ORM 用不上）、TIMESTAMPTZ（会错位）|
| 全局码表引用绑定（FK） | 跨表同码一处维护处处生效；删码表先解绑，无悬空引用 | 复制式下发到列（改一处要追 N 列，必腐化）|
| 指标口径轻量档（提示词注入） | 零执行层改动；无指标时提示词逐字不变，可灰度 | 指标引擎/语义层编译（要改 guard/executor，重）|
| 注释保存即重嵌入 | 管理动作低频，立即生效省掉运维脚本；同步 def 走线程池不卡事件循环 | 定时批量重建（生效延迟，多一个运维负担）|
| 页面触发同步 + 后台线程 | 管理员自助接入新表，不依赖运维上容器跑脚本；进程内互斥防并发写 | 只做 CLI（每接一张表找运维）|

MySQL/SQLite 元库支持已删除：`DATABASE_URL` 与 `DATASOURCE_DIALECT` 是启动必填。业务库方言仍由 `DATASOURCE_DIALECT` 控制（starrocks/mysql/postgresql）。

## 8. 已知边界与待决策项

诚实记录，不要在文档里被写成"已支持"：

1. **跨主体 JOIN 拦不住**。「按民族统计学生人数」模型可能把学籍表 LEFT JOIN 教职工表（本表专有编号跨主体关联），返回 0 行但 status=ok。已加提示词规则 9，实测无法根除。机械拦截需要"表间关系元数据"（哪两张表用哪个业务键关联），语义层目前没有这张关系表。待决策：加 `meta_join` 关系元数据后做硬校验。
2. **自助改口令 vs 管理员重置**：`PUT /api/auth/password` 写 `pwd_changed_at`（旧令牌立即失效），但 `scripts/set_password.py` 与 `PUT /api/rbac/users/{id}` 的重置**不写**，被重置者的旧令牌仍可活到 exp（最长 8h）。要么统一，要么在文档明示。
3. **播种 admin 的明文口令会进一次 WARNING 日志**（`rbac/service.py`）。首次播种无人交互，只能打印一次。生产建议显式配 `ADMIN_INIT_PASSWORD`，避免随机口令进日志。
4. **CORS 写死 localhost:5173**：部署形态靠 nginx 同源代理 `/api` 才不受影响；如果以后要让前端独立部署到局域网 IP 或域名，必须把允许来源改成环境变量。
5. **未使用的字段**：`meta_table.domain` 只展示不参与召回；`department.parent_code` 只记录不做树形继承；`metric.grain` 只进提示词不参与计算。UI 仍暴露它们，别在文档里承诺其效果。
6. **DDL 与 ORM 的差异**：`schema.postgres.sql` 是 10 张表的完整权威描述（含 `code_dict`、`metric`、全部 `COMMENT ON` 与种子 INSERT）。`create_all()` 对已存在的表只跳过不覆盖、不写注释，且个别索引不同（`ix_meta_column_name`、`ix_chat_turn_created_at`、`meta_column` 的 `ON DELETE CASCADE`、`chat_session` 的组合索引是 SQL 文件独有）。老环境升级靠启动时的 `ensure_meta_columns()` 补 `meta_column.code_dict_id`，`code_dict`/`metric` 表由 `create_all` 补建（无注释）。上线一律先跑 SQL 文件。
7. **历史回放的 SQL 块是空的**：`GET /api/history/{sid}` 的响应没带 `sql_guarded`，但前端读它。功能没坏（不影响提问），属于待修的小口子。
8. **冷启动竞态**：compose 的 backend 没有 `depends_on`/healthcheck 依赖 platform-pg，`init_db()` 在启动即执行，PG 未就绪时首启可能失败，重拉一次即可（见《部署文档》§6）。
9. **指标口径是提示词级约束**：模型仍可能不遵循表达式/默认条件，guard 不校验。要硬保证需指标引擎（待决策）。另外指标按"召回命中所属表"注入，问法与表注释不匹配时指标不会进提示词——指标生效的前提是召回质量。
10. **同步只增不删**：业务库删表/删列、或换业务库后，语义层旧行残留（页面没有删除表/列入口），残留表仍可能被召回。清理目前只能直接操作平台库，待决策：加语义层删除入口。
11. **同步任务状态在进程内存**：重启后进度归零（`idle`），但已写入平台库/向量的部分保留；重跑一次同步即可补齐（幂等，只增不覆盖）。
