# InsightAI ChatBI 部署文档

对应 2026-11-08 代码。四个 compose 服务：`backend`（FastAPI :8000）、`web`（nginx :8080→容器 80）、`platform-pg`（PostgreSQL 16 :5432）、`redis`（:6379）。

---

## 1. 前置条件

| 依赖 | 要求 | 说明 |
|---|---|---|
| Docker + Compose v2 | 支持 `docker compose` 子命令 | 本机镜像源走 daocloud；`minio` 类镜像需 pgsty 转发布 |
| 平台元库 | PostgreSQL 14+（compose 用 16-alpine） | 平台自有 **10 张表**；驱动 psycopg 3 |
| 业务库 | StarRocks（FE MySQL 协议）**必须只读账号** | 也可 `DATASOURCE_DIALECT=mysql/postgresql` 接其它库 |
| LLM | OpenAI 兼容端点（vLLM 等），内网可达 | 数据不出企业内网；无云端依赖 |
| Embedding | bge-m3 权重（1024 维），本地目录优先 | CPU 推理即可，镜像装的是 `torch 2.14.1+cpu` |
| Redis（可选） | 7.x | 单进程可留空退化为内存；多 worker/多副本必须配 |

端口占用：5432、6379、8000、8080。同机已有 PG/Redis 时改 compose 的 `ports` 或复用外部实例。

## 2. 配置 backend/.env

复制 `backend/.env.example` 为 `backend/.env` 后按环境填写。**口令与密钥只写在这个文件里，不要出现在命令行、代码或日志中。**

必填（缺任一项启动即报错）：

| 键 | 值 |
|---|---|
| `DATABASE_URL` | 容器内 `postgresql+psycopg://insight:insight@platform-pg:5432/insight`；宿主机直连把主机名换 `localhost` |
| `DATASOURCE_DIALECT` | `starrocks` / `mysql` / `postgresql`，同时用作 SQL 生成方言 |

业务库（`DATASOURCE_DIALECT=starrocks` 时用它拼连接串，不需要写 `DATASOURCE_URL`）：
`STARROCKS_HOST` / `STARROCKS_PORT`(默认 9030，按实际 FE 端口填) / `STARROCKS_DB` / `STARROCKS_USER`(只读账号) / `STARROCKS_PASSWORD`。
非 StarRocks 时才填 `DATASOURCE_URL`（完整 SQLAlchemy 连接串）。
（`.env.example` 里没逐一列出 `STARROCKS_*`，但 `config.py` 支持，直接写进 `.env` 即可。）

LLM：`LLM_BASE_URL`（到 `/v1` 为止）、`LLM_MODEL`、`LLM_API_KEY`（vLLM 无鉴权填 `EMPTY`）、`LLM_TIMEOUT`(60)、`LLM_TEMPERATURE`(0.0)、`LLM_MAX_TOKENS`(8192)、`LLM_ENABLE_THINKING`(false)、`SELF_CORRECT_RETRIES`(2)。
- `LLM_ENABLE_THINKING`：实测 4 题 false 0.7~1.5s、true 21~52s（贴 60s 超时上限），准确率无可测收益，默认 false；复杂多表题临时设 true。
- 思考模式打开时成功轮实测 1087~3489 tokens，**不要把 `LLM_MAX_TOKENS` 调到 8192 以下**，否则会撞截断并触发"模型未输出正文"错误。

向量：`LANCE_DIR`(默认 `data/lance`)、`EMBEDDING_PROVIDER=bge-m3`（目前只支持它）、`EMBEDDING_MODEL_DIR`（内网强烈建议指向本地权重目录，如 `data/models/bge-m3`；留空则用 HF 缓存/尝试联网）。

熔断：`QUERY_ROW_LIMIT`(1000)、`QUERY_TIMEOUT`(10)。

登录/JWT：`TOKEN_SECRET`（**生产必须设固定值**，留空则每次启动随机、重启即全员重新登录）、`TOKEN_TTL_MINUTES`(480)、`LOGIN_MAX_FAILS`(5)、`LOGIN_LOCK_MINUTES`(15)、`LOGIN_RATE_PER_MINUTE`(5)、`REDIS_URL`（容器内 `redis://redis:6379/0`，留空=进程内存）、`ADMIN_INIT_PASSWORD`（首次播种 admin 用；留空则随机生成并**打印一次到 WARNING 日志**，生产建议显式设置以免明文口令进日志）。

换业务库（改 `STARROCKS_DB` 等）后重启 backend 并重新同步即可；注意**同步只增不删**，旧库的语义层行会残留（见 §8）。

## 3. 建平台元库

1. 起数据库：`docker compose up -d platform-pg`（首次会创建 `pgdata` 卷，用户/口令/库名都是 `insight`）。
2. 建库（compose 已建 `insight` 库，若用外部实例由 DBA 执行）：
   `CREATE DATABASE insight ENCODING 'UTF8' LC_COLLATE 'C.UTF-8' LC_CTYPE 'C.UTF-8' TEMPLATE template0;`
3. **执行 `backend/schema.postgres.sql`**（推荐路径，索引与列注释比 ORM 建的表更全）：
   ```bash
   docker compose exec -T platform-pg psql -U insight -d insight < backend/schema.postgres.sql
   ```
   （外部实例同理用 `psql "postgresql://<user>:<pwd>@<host>:5432/insight" -f backend/schema.postgres.sql`；注意该文件没在镜像里，被 `backend/.dockerignore` 排除了。）
   注意事项：
   - 该文件现在是 **10 张表的完整权威 DDL**（含 `code_dict`、`metric`）+ 全部 `COMMENT ON` + 文件末尾的种子 INSERT。
   - **种子 INSERT 是真实语句不是注释**：内置角色 `admin`/`user`、演示部门 `DEMO_RLS`（单位码 1005/100204/200205/2007）、`admin` 与 `demo_rls` 两个账号（口令哈希对应开发环境口令）。全新环境执行后必须：立即改 admin 口令、删除或停用 demo 账号与演示部门；不需要演示数据就删掉文件末尾这几条 INSERT 再执行。应用启动时 `seed_defaults()` 只在没有可用管理员时才播种 admin，不会覆盖已有账号。
   - 应用启动时 `init_db()` 的 `create_all()` 对**已存在**的表只跳过、不覆盖，所以先跑 SQL 文件才能保住列序/索引/`COMMENT ON`。
   - 时间列一律 naive UTC + `TIMESTAMP`（不要改成 `TIMESTAMPTZ`，否则锁定窗口与旧令牌判定错位）。
   - `audit_log.rows` 用了带双引号的保留字列名，建表和引用都保留双引号。
   - 改模型时必须同步改两份描述：`schema.postgres.sql`（注释的唯一来源）与 `app/models/` ORM（`create_all` 不写 `COMMENT ON`）。
   - 该文件里 `meta_column` 的 `ON DELETE CASCADE`、`ix_meta_column_name`、`ix_chat_turn_created_at`、`chat_session` 的 `(user_id, updated_at)` 组合索引是 SQL 文件独有的；若某环境是让 app 自动建表，这些约束不存在——两套环境的 DDL 行为差异要清楚。
4. 冒烟确认建表成功：`\dt` 应看到 `meta_table、code_dict、meta_column、metric、department、role、app_user、chat_turn、chat_session、audit_log` 共 **10 张**。

**老环境升级**（已有 8 张表的库）：不要直接重跑整个 SQL 文件（CREATE TABLE 会报已存在）。启动新版 backend 即可——`ensure_meta_columns()` 自动给 `meta_column` 补 `code_dict_id` 列，`create_all()` 自动补建 `code_dict`/`metric` 表（无注释，介意就手工对照 SQL 文件补 `COMMENT ON`）。

## 4. 构建与启动

```bash
docker compose up -d --build         # 首次全量构建并启动
docker compose ps                    # 4 个服务 Up
curl http://localhost:8000/api/healthz   # {"ok":true}
```
浏览器访问 `http://localhost:8080`，用 `admin` + `ADMIN_INIT_PASSWORD`（或日志里打印的一次性口令；若是跑 SQL 文件 seeds 出来的 admin，口令是开发环境那个，必须立即改）登录后立刻改口令。

**改代码必须重新构建再重启对应服务**（代码烧进镜像，容器里没有挂载源码，只挂了 `./backend/data`）：
```bash
docker compose build backend && docker compose up -d backend      # 后端改动
docker compose build web && docker compose up -d web              # 前端改动
```
- **不要用 `docker compose down`**：会把自建镜像 tag 丢掉，下次要全量重建（重建 torch/sentence-transformers 很耗时）。停服务用 `docker compose stop <svc>`。
- 也不要 `down -v`：`pgdata` 与 `backend/data`（向量索引）都在卷/挂载里，删卷即丢数据。
- 看日志：`docker compose logs -f backend`。健康检查每 15s 打 `/api/healthz`；该接口只回 `{"ok":true}`、**不探测 LLM/业务库**，所以容器 unhealthy 说明进程本身没起来或卡死，直接看启动日志。

## 5. 接入业务表元数据（管理员的一次性流程）

**推荐路径：页面操作，不需要上服务器跑脚本。**

1. 管理员登录 → 顶部「语义管理」。
2. 「同步前缀」填要开放的表名前缀（逗号分隔，如 `dwd_,dws_`；**留空 = 全量同步库里所有表**，几百张表的向量化要几分钟）→ 点「同步元数据」。按钮变「同步中…」，黄条实时显示进度，完成后自动刷新表清单。重复点击会报「已有同步任务在运行」（409），等当前任务完成即可。
3. 同步行为：从业务库 `information_schema` 拉表/列；前缀按表名小写开头匹配；**只增不覆盖**——已有列的注释/码表/敏感标记不动、表注释只补空、业务库消失的表/列不删；新列按关键词自动标敏感（身份证/手机号/薪资等）；`dwd|ads|dws` 开头自动归 `trade` 域；同步范围内全部表/列向量自动重算。
4. **手工补齐三件事**（直接决定问答质量，全部在页面上做）：
   - **中文注释**：表注释在顶部输入框「保存注释」；列注释在列行「编辑」弹窗里改。**保存即自动重嵌入向量，立即参与召回，不需要跑重建脚本。**
   - **码表**：跨表通用码去「全局码值」建码表 →「批量绑定」按列名匹配绑定（同名不同义的列取消勾选）；列特有的码在列编辑弹窗填本地码值（本地覆盖全局同 key）。「从业务库拉取码值」可带回最多 50 个真实 DISTINCT 值。
   - **行级权限列**：逐表设「行级权限列」→「保存表设置」。**新同步的表默认不设 = 不裁剪，开放给普通用户前必须逐表确认。**
5. 指标口径（可选）：「指标口径」页定义统一口径（表达式 + 默认条件 + 别名），提问命中所属表时注入提示词。属提示词级约束，上线后实测核对 SQL（见《使用文档》§9.3）。

**CLI 备选路径**（容器内已装齐依赖；本机跑脚本才需要下面的 venv）：

```bash
cd backend && python -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
pip install "psycopg[binary]" redis                              # requirements 已列，本机 venv 可能缺，补上
pip install torch==2.14.1+cpu --index-url https://download.pytorch.org/whl/cpu
pip install sentence-transformers                                # 后三者只在 Dockerfile 里，不在 requirements.txt
```

- 探查业务库：`python scripts/sync_starrocks_meta.py --probe` → 打印库里的表与行数。
- 同步指定表：`python scripts/sync_starrocks_meta.py --sync dwd_xb_xjjbsj,dwd_xb_dwjbsj`；或 `--sync-all [--max-tables 20]`。**CLI 没有前缀参数**，前缀过滤只在页面/API（`POST /api/meta/sync {"prefixes":["dwd_"]}`）。
- 重建/检查向量索引（日常不需要——注释保存已自动重嵌入；只在换 provider 或索引损坏时用）：
  ```bash
  python scripts/reindex_vectors.py --check    # 只打印 provider/dim/index_dim
  python scripts/reindex_vectors.py            # 增量 merge-insert（不会删除已消失的旧行）
  python scripts/reindex_vectors.py --drop     # 破坏性：删掉整个 vecs 表后重建
  ```
  维度不一致时脚本以退出码 2 中止并提示加 `--drop`；**换 `EMBEDDING_PROVIDER` 必须 `--drop` 重建**。
- 口令管理：`python scripts/set_password.py admin`（两次 getpass，不回显）或 `--generate` 打印一次性随机口令。
  ⚠ 该脚本与"管理员在权限管理页重置口令"**都不会写 `pwd_changed_at`**，被重置者已登录的令牌仍可活到过期（最长 8h）。要立即踢人，只能让用户自己走一次「修改口令」，或另想方案。

## 6. 部署后验证清单

按顺序做，每步都有明确预期，别只看容器 Up：

| # | 动作 | 预期 |
|---|---|---|
| 1 | `curl :8000/api/healthz` | `{"ok":true}` |
| 2 | 查 backend 启动日志 | 无 `初始管理员已就绪` 之外的 WARNING；若出现 `TOKEN_SECRET` 随机提示说明没配密钥 |
| 3 | 页面登录 admin | 顶部显示"· 管理员"，出现「语义管理」「全局码值」「指标口径」「权限管理」四个入口 |
| 4 | 语义管理 → 同步元数据（先填一个窄前缀试） | 黄条显示进度，完成后表清单出现匹配的表；再点一次同步期间重复触发报 409 |
| 5 | 改一个列注释保存 → 提问用到该列 | 保存成功（稍等片刻是在重嵌入）；提问能召回该列，**无需跑 reindex** |
| 6 | 全局码值 → 建测试码表 → 批量绑定一个列 → 提问 | 结果里码值显示为含义；删测试码表后绑定列自动解绑 |
| 7 | 指标口径 → 建测试指标 → 用指标名提问 | SQL 折叠区绿色那条采用定义的表达式与默认条件；验完删除测试指标 |
| 8 | 权限管理 → 部门 → 建/改一个测试部门，单位码集合填真实单位码；**并给目标表设行级权限列** | 保存成功；单位码 >50 时报 422 |
| 9 | 新建普通用户（口令留空自动生成）并用它登录 | 顶部显示"· N 个单位码"；无管理入口 |
| 10 | 普通用户提问「按单位统计学籍数量」 | status=ok；展开 SQL 折叠区，绿色那条**必须含 `IN ('…')` 或部门等值条件**与 `LIMIT 1000`（前提：相关表已设部门列） |
| 11 | 同一账号问「列出教职工的姓名和身份证号」 | 身份证列显示为部分掩码，且有「敏感列已脱敏」提示；admin 问同一句应显示原文 |
| 12 | 问「休学类的学籍异动有多少条」 | SQL 里用码值（如 `WHERE ydlbm='11'`），结果显示"休学"（含义翻译） |
| 13 | 问一个表里没有维度的问题（如「按性别统计学生人数」） | 返回「当前数据里没有可以回答该问题的字段：…」，**不能**返回一个口径被偷偷改掉的成功结果 |
| 14 | 追问「用饼图展示」 | 复用上一轮口径重跑，不被当闲聊拒答；结果形状符合时出图 |
| 15 | 会话：新建/重命名/删除，并用另一个账号尝试访问该会话 ID | 重命名即时生效；删除后历史清空；跨账号提问 403、读历史返回空 |
| 16 | `audit_log` 最新一行 | `sql_raw` 与 `sql_guarded` 两条都在，`status`、`rows`、`elapsed_ms` 合理 |
| 17 | 冷启动顺序 | 若 backend 先于 PG 就绪导致启动失败（compose 没有 `depends_on`），`docker compose restart backend` 一次即可 |

## 7. 备份与恢复

```bash
# 平台元库（语义层 + 码表 + 指标 + 部门/角色/账号是最需要保的）
docker compose exec -T platform-pg pg_dump -U insight -d insight > platform_pg_backup.sql
# 恢复
cat platform_pg_backup.sql | docker compose exec -T platform-pg psql -U insight -d insight
```
- 备份前先确认是否要覆盖在线数据；恢复会抹掉语义层的注释/码表/指标/部门/账号维护成果，生产操作前务必二次确认。
- 向量索引随 `backend/data/lance/` 一起备份（挂载目录，删卷会丢）；丢了可以用 `reindex_vectors.py --drop` 重建，不需要备份模型权重（`data/models/bge-m3` 另存）。
- `chat_turn`/`audit_log` 会持续增长，按需归档；`audit_log` 是合规留痕，删之前确认审计要求。

## 8. 故障排查

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动即 `PydanticValidationError: database_url / datasource_dialect` | 必填项缺失 | 补 `.env`；注意 `.env` 已被 `.dockerignore` 排除，不会进镜像，靠 `env_file` 注入 |
| 本机 venv 起不来：`ModuleNotFoundError: psycopg` | `requirements.txt` 写了但本机未装 | `pip install "psycopg[binary]" redis` |
| 首次提问特别慢或 embedding 报错 | `torch`/`sentence-transformers` 只在 Dockerfile 装、且权重首次加载 | 本地跑脚本时按 §5 补装；配 `EMBEDDING_MODEL_DIR` 指向本地权重 |
| 同步按钮报「已有同步任务在运行」 | 进程内互斥，已有任务在跑 | 等黄条显示完成；重启 backend 后状态归零可重跑（幂等，只增不覆盖） |
| 同步完成但 0 张表 | 前缀不匹配（按表名小写开头匹配） | 看黄条「前缀过滤: N → 0」；核对前缀拼写，或留空全量 |
| 保存注释要等几秒 | 保存即重嵌入（CPU 推理） | 正常；单列秒级，整表摘要稍慢 |
| 指标口径没生效 | 提问没召回命中所属表；或模型没遵循（提示词级约束） | 补表/列注释提高召回；展开 SQL 折叠区核对表达式 |
| 码值没翻译成含义 | 列没绑定码表 / 本地码值覆盖了全局 / key 不匹配 | 语义管理看该列「枚举码表」列；确认生效码值（全局+本地覆盖） |
| 换业务库后旧表还在语义层 | 同步只增不删 | 直接清理平台库 `meta_table`/`meta_column` 旧行并重算向量（页面暂无删除入口） |
| `模型未输出正文（finish_reason=length…）` | 输出被 `LLM_MAX_TOKENS` 截断（多为思考模式） | 调大 `LLM_MAX_TOKENS` 或 `LLM_ENABLE_THINKING=false` |
| `[engine_error] LLM 请求失败: ConnectError（60s 超时上限，已试 N 次）` | LLM 端点不可达/超时 | 检查 `LLM_BASE_URL`、网关、`LLM_TIMEOUT` |
| `索引向量维度与当前 embedding 不一致` | 换了 provider 或旧索引残留 | `python scripts/reindex_vectors.py --drop` |
| 提问一直 403「该账号未绑定部门数据权限」 | 部门没单位码集合 | 权限管理 → 部门 → 填单位码 |
| 查不到数据但 SQL 看起来对 | 部门列没配 / 单位码与业务库实际值不匹配 | 语义管理确认该表 `dept_column`；核对业务库里该列的真实取值 |
| 登录 423 | 账号连错 5 次锁定 | 等 15 分钟或管理员用脚本重置（注意 §5 的旧令牌说明） |
| 重启后所有人都要重新登录 | 没配 `TOKEN_SECRET` | 设固定密钥 |
| 前端能开、接口全 502 | nginx 反代 `http://backend:8000` 解析不到服务名 | 服务名必须是 `backend`；检查 compose 服务名与网络 |
| 从局域网 IP 访问页面正常、接口报 CORS | `main.py` 里 CORS 只写了 `localhost:5173` | 生产走 nginx 同源代理 `/api` 不受影响；若前端独立部署需把允许来源改成可配置项 |
| 多副本部署后退出登录仍能用的令牌没立刻失效 | 没配 `REDIS_URL`，吊销表在各自进程内存 | 配 `REDIS_URL=redis://redis:6379/0`（Redis 读失败时逻辑是"当作未吊销"放行，属已知取舍） |

## 9. 上线安全核对
